# First physical ESP32-S3 USB bring-up — Canonical Profile B v0.1

Owners: Ege and the AuscultaForge team (firmware/desktop); Kaan (board inspection
and later acoustic integration). Historical Ozan review/submission credits do not
assign active implementation ownership. Physical verification remains **PENDING**.

Read [the protocol audit](../../../firmware/PROTOCOL_AUDIT.md),
[firmware build/runtime instructions](../../../firmware/README.md), and
[canonical wire specification](../protocol/B_C_CANONICAL_PROTOCOL_V0_1.md).
The obsolete version of this guide contained incompatible HELLO, encoding,
profile and waveform values. The audit records their resolution.

## 1. Identify the purchased board before connecting anything

- Photograph both PCB sides, ESP32-S3 module marking, seller/model code DSTK22852,
  PCB revision, connector labels, bridge-chip markings and BOOT/RESET buttons.
- Confirm ESP32-S3-WROOM-1-N16R8; quantity purchased does not establish PCB identity.
- Use a known USB data cable. Observe one connector at a time in Windows Device
  Manager (`devmgmt.msc`); record Hardware IDs, device instance path and COM number.
- Distinguish a CP210x/CH34x UART bridge from the S3's native USB Serial/JTAG
  controller. Labels alone are insufficient. Match schematic or continuity/routing
  evidence to the purchased PCB. Do not assume the official DevKitC connector map.
- The SoC's native USB D-/D+ are GPIO19/20. OTG CDC firmware and internal USB
  Serial/JTAG share the internal PHY. Selecting OTG in software can make the ROM
  debug COM port disappear and create a different application CDC COM port.
- Do not connect both USB ports or an independent power source until power paths
  and backfeed protection are known. This firmware assumes bus-powered native USB;
  an independently powered board requires reviewed VBUS sensing, not a guessed GPIO.
- Do not wire the microphone for G1. GPIO4/5/6 are only a provisional BCLK/WS/DIN
  proposal. Confirm every physical header first; GPIO35..37 are PSRAM-reserved.

See [Espressif S3 USB Serial/JTAG limitations](https://docs.espressif.com/projects/esp-idf/en/v5.5.1/esp32s3/api-guides/usb-serial-jtag-console.html)
and [S3 USB hardware](https://docs.espressif.com/projects/esp-idf/en/v5.5.1/esp32s3/api-reference/peripherals/usb_device.html).
No eFuse changes, secure boot, flash encryption or irreversible configuration.

## 2. Install the pinned Windows toolchain

Use the [official ESP-IDF Windows setup prerequisites](https://docs.espressif.com/projects/esp-idf/en/v5.5.1/esp32s3/get-started/windows-setup.html)
(Git, supported Python, and ESP-IDF tools installer if prerequisites are absent).
Python 3.11 is a suitable baseline. In PowerShell, use a new installation folder:

```powershell
$afIdf = 'C:\Espressif\frameworks\esp-idf-v5.5.1'
git clone --branch v5.5.1 --recursive https://github.com/espressif/esp-idf.git $afIdf
& "$afIdf\install.bat" esp32s3
. "$afIdf\export.ps1"
idf.py --version
xtensa-esp-elf-gcc --version
```

Expected IDF: v5.5.1. IDF's own tools.json selects Xtensa GCC 14.2.0,
`esp-14.2.0_20241119`; do not substitute desktop MSYS GCC for firmware compilation.
If the directory already exists, verify its tag/submodules instead of overwriting it.
Use the official installer terminal if local PowerShell execution policy prevents
export.ps1; do not weaken machine-wide execution policy.

## 3. Configure and build without a board

From the exported IDF shell:

```powershell
Set-Location C:\Dev\Antigravity\bitirme\ausculta-forge\firmware
New-Item -ItemType Directory -Path build -Force | Out-Null
idf.py set-target esp32s3 2>&1 | Tee-Object build\set-target.txt
idf.py build 2>&1 | Tee-Object build\build-output.txt
```

Check each command's exit code and actual compiler errors; a log file alone is not
a pass. `set-target` resets an existing sdkconfig; preserve any local configuration
first. Expected: 16 MB flash, octal PSRAM, UART0 console, no secondary USB console,
one CDC interface, 4096-byte RX/TX/endpoint buffers. Review the generated sdkconfig.
Do not tune PSRAM voltage or flash/octal modes by guessing board pins.

The exact managed versions are esp_tinyusb 2.2.0 and tinyusb 0.19.0~3.
The checked-in `firmware/dependencies.lock` was generated by Component Manager
2.4.11 against the real registry for declared IDF 5.5.1 / esp32s3. Review versions,
component hashes and target; preserve the lock during the real build. Standalone
dependency resolution is not firmware compilation: current build status remains
**COMPILED BUT NOT FLASHED** for the 2026-10-23 First Contact release; see FIRST_CONTACT_RELEASE.md for actual evidence.

Save `build/project_description.json`, `build/flasher_args.json`, `sdkconfig`,
`dependencies.lock`, `idf.py --version`, compiler version, build log and binary hash:

```powershell
Get-FileHash build\auscultaforge_g1.bin -Algorithm SHA256
```

Only a zero-exit ESP-IDF build changes status to **COMPILED BUT NOT FLASHED**.

## 4. Positively identify the programming interface

Close the desktop/serial monitors before identifying a programming COM port.
Use only the connector identified in step 1. If ROM download mode is needed,
verify the BOOT and RESET labels, hold BOOT, press/release RESET, then release BOOT.
Record the newly enumerated port. Replace the following placeholder with that
verified port; do not paste `COM_VERIFIED` literally:

```powershell
python -m esptool --chip esp32s3 --port COM_VERIFIED chip-id
python -m esptool --chip esp32s3 --port COM_VERIFIED flash-id
```

These are read-only identity queries (they may reset into ROM download mode).
Confirm chip model, MAC and 16 MB flash against board evidence. Never select an
unidentified device because its COM number resembles a previous session.
Flash only after those checks and a successful build:

```powershell
idf.py -p COM_VERIFIED flash
```

Keep the flash log. Flashing overwrites the configured application/partition
regions; preserve any pre-existing firmware/data required by the team first.
No erase-flash operation is needed for normal G1 flashing.

## 5. Observe debug logs and identify the application CDC port

Firmware logging uses UART0 only. If a separate UART bridge and its power routing
have been verified, use that bridge for `idf.py -p COM_DEBUG monitor`. Otherwise
run with only the native USB cable and inspect logs later using a reviewed UART
adapter arrangement. Never open a monitor on the binary application CDC port.

Current 1.1.0 UART logs report Canonical B readiness, reviewed-profile I2S availability,
pending physical G1/G2, state/session/sample/frame counters and queue/heap/stack health.
Do not expect fabricated endpoint addresses or per-packet hexdumps.

After exiting ROM/restarting, rescan Windows ports. Identify the firmware's CDC
interface by observed enumeration and product `AuscultaForge G1` / interface
`Canonical Profile B`, together with the recorded physical port and Hardware IDs.
Default development descriptors are not a unique board identity; do not hardcode
VID/PID or COM number. A different COM port from ROM is normal. DTR must be asserted
by the host. USB is **full-speed (12 Mbit/s)**; virtual serial baudrate is not the
USB transfer rate. Logs and protocol data must remain on separate interfaces.

## 6. Verify exact canonical constants

All multibyte fields are little-endian; CRC is IEEE CRC32, reflected polynomial
0xEDB88320, init/final XOR 0xFFFFFFFF, covering header plus payload.

| Item | Exact value |
| --- | --- |
| Magic / version | 0xAF534331 / 1 |
| Header / CRC trailer | 40 / 4 bytes |
| Rate / channels / precision | 48000 / 1 / signed 24-bit in S32LE |
| Profile B ID / LSB encoding | **2 / 1** |
| HELLO_REQ / HELLO_ACK | **0x10 / 0x11**, payload **4 / 24** bytes |
| START_REQ / START_ACK | 0x03 / 0x04, payload 16 / 32 bytes |
| AUDIO | 0x01, 256 samples, 1024-byte payload, 1068-byte packet |
| STATUS | 0x02, 72-byte payload |
| STOP_REQ / STOP_ACK | 0x05 / 0x06, payload 8 / 72 bytes |
| ERROR | 0x0F, 8-byte payload |
| Control sample_count | Always zero |
| Source mode | **1** deterministic; mode **0 rejected without reviewed I2S profile** |

HELLO nonce is **32-bit**, echoed exactly. START carries rate, target, source,
encoding, channels and profile; STOP carries the active **64-bit session ID**.
The normative source is `u=(n*16807+7)&0xffffff`; if `u&0x800000`, sample is
`u-0x1000000`, otherwise `u`. Reference samples: n=0 -> 7; n=1 -> 16814;
n=500 -> -8373709; n=1000 -> 29791; n=479999 -> -2497696.

## 7. Perform HELLO and full physical G1 through Desktop

1. Launch the existing desktop/backend using its normal development/release
   instructions. In Device view, Scan USB Bus and select the positively identified
   **application CDC data COM port**.
2. Connect & HELLO. Save the returned nonce/capabilities and session diagnostics.
   A successful HELLO alone is not a physical G1 pass.
3. Select Deterministic G1 (mode 1). Start with 480000 target samples. Expect a
   nonzero fresh session ID, encoding 1, channels 1, profile 2 and 48000 Hz.
4. Watch counters for approximately 187.5 AUDIO frames/s. At 10 seconds expect
   **480000 samples and 1875 AUDIO frames**. STATUS frames do not count as AUDIO.
5. Wait for the host accepted-sample counter to reach 480000, then Stop Acquisition.
   The firmware has stopped generation at target and waits for this STOP_REQ.
   It drains queued data before STOP_ACK. Do not disconnect before ACK arrives.
6. Require 100% normative sample match; zero CRC errors, gaps, duplicates and
   index discontinuities; final telemetry generated=fully_queued=480000,
   dropped=0, frames=1875, audio_bytes_queued=2002500, error_code=0,
   dma_overflow_events=ring_overflow_events=usb_timeout_events=0,
   stop_reason=0 (target) or 1 (host stop). Record partial-write counters rather
   than confusing retry events with dropped data.
7. Save the G1 verification evidence JSON, actual session metadata/WAV if recorded,
   support bundle, UART/flash/build logs, board/port photographs, firmware hash,
   host commit and firmware commit. Verify the evidence identifies physical USB,
   not loopback. Synthetic pacing does not prove physical I2S sample-clock accuracy.
8. Only now record **PHYSICAL G1 PASSED** for that exact board/firmware/host run.

An independent physical acceptance run can be made after Desktop releases the COM
port (repository root; substitute the verified data port):

```powershell
.venv\Scripts\python.exe tools\protocol_lab\module_b_package\verify_g1_bringup.py --port COM_DATA_VERIFIED --seconds 10 2>&1 | Tee-Object physical-g1-console.txt
```

This CLI prints a report; it does not automatically save a metrics JSON. Preserve
the console log and use Desktop's evidence/support export for structured evidence.
`--synthetic` is a software dry run and must never be described as physical proof.

## 8. Failures and safe recovery

- Port busy: close only the identified competing serial process. Never terminate
  every Python process on the workstation.
- HELLO timeout: verify native routing, firmware boot, DTR, selected application
  COM and cable. Retry connect if a probe coincided with close/reopen reset.
- Wrong nonce: host rejects stale/corrupted HELLO; close/reopen and capture raw
  diagnostics. The device must echo the received uint32, not a constant.
- Mode 0: unsupported by design. Do not interpret synthetic samples as microphone
  data. Wrong format/configuration/session gets ERROR, never a silent fallback.
- CRC/continuity/drop errors: save the failing evidence. Check buffer pressure,
  power and cable; a retry must produce a new full evidence run, not a patched pass.
- Unplug/suspend/DTR close or a one-second TX stall: acquisition is invalidated.
  Close/reopen, HELLO, START again. Do not append a new session to interrupted data.
- No application enumeration or bad firmware: disconnect optional peripherals,
  enter verified BOOT/RESET ROM download mode, rediscover and re-identify the chip,
  then reflash a known successful build through the confirmed programming route.
  USB Serial/JTAG can return in ROM even after OTG claimed the PHY in the app.
  A reviewed UART bridge is the alternate recovery route if this PCB exposes one.
- Do not burn USB PHY eFuses, disable ROM download, enable secure boot/encryption,
  or change flash/PSRAM voltage to recover. If pin/power routing is unclear, stop
  physical manipulation and resolve the board documentation first.
